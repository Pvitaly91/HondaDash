# M1: розширення synthetic-demo-v1

Це власні команди керування синтетичним тестовим endpoint. Вони не є
командами Honda, DLC, ECU або датчиків автомобіля. Фізичне підключення USB
не змінює походження даних: `synthetic-demo-v1`, simulation.

## Сумісний базовий кадр

Формат [M0](DEMO_PROTOCOL.md), SOF `A5 5A`, версія `01`, little endian,
CRC-16/CCITT-FALSE, HELLO `01/81`, READ_SNAPSHOT `02/82` та 21-байтовий
snapshot залишаються незмінними. Максимум payload — **64 байти**,
повний кадр — **79 байтів**. Незалежні golden fixtures M0 збережено.

HELLO має порожній payload. Відповідь точно `01` + ASCII
`synthetic-demo-v1`, без NUL. Лише після цього допустимі snapshots та
розширені команди. Після reset firmware READ повертає `FF {03}` і потребує
нового HELLO. Відкриття COM-порту саме по собі не підтверджує протокол.

## Команди extension version 1

| Запит / відповідь | Payload запиту | Payload відповіді |
|---|---|---|
| `10 / 90` GET_DEVICE_INFO | Порожній | Опис нижче |
| `11 / 91` SET_SCENARIO | scenario u8, seed u32 LE | `00` ACK |
| `12 / 92` SET_MANUAL | 7 × signed i16 LE, рівно 14 байтів | `00` ACK |
| `13 / 93` SET_FAULTS | silent u8, delay_ms u16 LE, once_flags u8 | `00` ACK |
| `14 / 94` SET_QUALITY | 7 × status u8 | `00` ACK |

Device info: `[extensionVersion, endpointKind, major, minor, patch,
capabilitiesLow, capabilitiesHigh]`, далі ASCII implementation без NUL.
Firmware M1: `[1, 2, 0, 2, 0, 0x0f, 0] + "nano-synthetic"`.
Desktop: kind `1`, implementation `desktop-emulator`, та сама версія `0.2.0`.
Kind `2` є декларацією endpoint; handshake не є криптографічним доказом
того, яка саме плата чи USB-перетворювач відповідає.

Capabilities u16: bit 0 — SET_SCENARIO, bit 1 — SET_MANUAL, bit 2 —
SET_FAULTS, bit 3 — SET_QUALITY. Невідомі біти не надають нових можливостей
клієнту. UI вимикає можливості, яких endpoint не оголосив.

Scenario: `0` ignition, `1` idle, `2` demo, `3` manual. SET_SCENARIO
одночасно встановлює seed та починає часовий цикл заново. Значення manual
і якості зберігаються при зміні сценарію. ACK не є вибіркою даних.

SET_MANUAL задає **всі сім** scaled words атомарно, у порядку M0:
rpm, speed, coolant, intake, throttle, map, voltage. Scale:
`1, 10, 10, 10, 10, 10, 100`. Межі words:
`0..12000, 0..2500, -400..1500, -400..1200, 0..1000, 0..2500, 0..2000`.
Поганий word відхиляє всю команду. Приклад ручних значень
2345, 67.8, −12.3, 28.4, 56.7, 98.7, 13.45:

```text
29 09 A6 02 85 FF 1C 01 37 02 DB 03 41 05
```

SET_QUALITY приймає лише `01` Valid, `03` Unsupported, `04` Invalid.
Недоступні канали у snapshot завжди мають sentinel `00 80`, а не нуль.
Властивості NoData/Stale та час отримання визначає ПК.

## Несправності та можливість відновлення

`silent` — 0 або 1; `delay_ms` — 0..5000; `once_flags`: bit 0 пошкоджує
CRC наступного snapshot, bit 1 залишає лише першу половину snapshot.
Обидва біти дозволено поєднати; спочатку псується CRC, потім обрізається
кадр. Невідомі біти відхиляються. SET_FAULTS повністю замінює ці настройки.

Несправності стосуються **лише успішних SNAPSHOT_RESPONSE**. HELLO,
device info, ACK та ERROR залишаються доступними. Silent не споживає
once_flags; вони споживаються при формуванні наступної видимої відповіді.
Зміна контролів проходить тим самим планувальником, після завершення
поточного запиту або його тайм-ауту. ACK не освіжає модель.

Endpoint має окремий фіксований слот відкладеного snapshot. Контрольна
команда може отримати ACK, поки цей слот очікує; новий READ у цей час
отримує Busy. Зміна delay/silent не змінює вже запланований кадр. Коли
старий кадр надійде після deadline, Session відхилить його за request ID.
Новий HELLO з іншою session identity скасовує старий відкладений кадр.

## Помилки, повтори та обмеження

ERROR_RESPONSE `FF`, payload один байт:

| Код | Значення |
|---|---|
| `01` | Непідтримуваний тип операції |
| `02` | Неправильний розмір або значення payload |
| `03` | HELLO ще не пройдено, reset або інша session identity |
| `04` | Busy / вичерпано bounded transport capacity |
| `05` | Старий request ID або той самий ID з іншими байтами |

Помилки CRC, version або length >64 не отримують відповіді. Parser
відновлюється на наступному повному коректному кадрі; один SOF усередині
payload не означає новий кадр. Формат не передбачає вкладених кадрів.

В одній session request ID зростає; перед переходом u32 через нуль
клієнт відкриває нову session identity. Endpoint зберігає останній повний
запит і вже сформовані байти його відповіді. Точний дублікат повторює
ці байти без повторної зміни сценарію, seed чи одноразового fault.
Дублікат відкладеного READ не пересуває deadline. Дублікат silent READ
також мовчить. Старіші операції не виконуються повторно.

Nano має RX 79 байтів, TX 158 байтів, cache request/response по 79 байтів
та один delayed buffer 79 байтів. Якщо несправний peer надсилає запити
швидше, ніж читає відповіді, endpoint очищує заповнену TX-чергу,
скасовує delayed state, повертає Busy `04` та вимагає нового HELLO.
Командна дія не виконується без резерву під відповідь. Нормальний
клієнт завжди має лише один активний запит. Лічильники saturate на
UINT32_MAX; пам’ять не зростає.

## Сценарії firmware

Ручні значення та wire encoding Nano збігаються з desktop точно.
Ignition: 0 rpm, 0 km/h, 22 °C, 22 °C, 0%, 100 kPa, 12.50 V.
Idle використовує цілочисельну детерміновану варіацію rpm 836..864;
інші значення 0, 85, 30, 2, 32, 14.20. Це демонстраційні формули.

Demo має той самий 80-секундний поділ фаз M0: 0–3 с ignition,
3–5 запуск, 5–25 прискорений прогрів, 25–60 зміна навантаження,
60–70 idle, 70–80 зупинка. Nano замінює desktop cosine цілочисельною
трикутною хвилею та спрощує варіацію температури/напруги. Це явна
відмінність моделей, а не похибка wire scaling і не характеристика Honda.

Сценарій використовує час firmware `uint32_t millis()`; elapsed і
короткі deadlines обчислюються unsigned subtraction через wrap-around.
Повний період u32 часу близько 49.7 діб обмежує неперервність epoch;
на цій межі демоцикл починається заново. Час отримання snapshot на ПК
монотонний і має інший початок; ці часові шкали не порівнюються.
